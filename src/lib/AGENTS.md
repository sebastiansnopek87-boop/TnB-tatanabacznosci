- Active UI calls use `src/lib/api/*` browser adapters. Migrated modules invoke Supabase Edge Functions directly; do not add new UI imports from `*.functions.ts` or `*.server.ts`. Remaining legacy server modules are retained only for rollback and existing regression tests until their coverage is moved to Edge Function tests.
- Admin e-mails: notifications.server.ts, configured by single-row email_settings, logged to email_notification_log.
- Control Center uses read-only queries, shared hasAccess, slug/title search and separate order/admin/mail history offsets with a frozen time boundary; mail links only by related_id, actor history stays separate. Tests use vitest.control-center.config.ts without the RPC transform. Why: data integrity, one access truth and testable read handlers without new registries.
- Newsletter stores consent text/version/time + opt-in method; active only when the opt-in rule is satisfied.
- Community: guests read only public+published posts via anon RLS/column grants (no author_id); writes authenticated-only.
- Library: metadata in library_items (anon, published); content in library_item_content gated by library_can_read(); files via signed URLs, covers via the existing public asset Edge Function (`tnb-assets`). Premium = paid library_orders row, never the premium role.
- Orders/payments: browser adapters use `tnb-orders` and `tnb-payments`; P24/Tpay/PayU callbacks are signature-verified in the Edge Function, deduplicated in `payment_webhook_events`, and checked for amount/currency before status changes (`needs_review` on mismatch). `paid` is granted only by verified provider confirmation or admin confirmation of a bank transfer. Access = `paid_at` set, `access_revoked_at` null, status `paid`/`refund_pending`/`refunded`; linked to `user_id` or confirmed account e-mail.
- Meetings: all 16 public, participant and admin actions use `tnb-meetings`; public reads keep `online_link` hidden, registrations retain honeypot, per-email uniqueness and DB capacity trigger.
- Podcast: admin-only RLS; public reads via safe columns; episode media is returned through the module Edge Function only after access checks; signed/private media paths must never be exposed in public columns.
- Podcast navigation uses the existing published catalogue: sort_order then ascending publication date, category-first recommendations, no repeated IDs/slugs or current/adjacent recommendations; Media remounts per episode. Why: reuse editorial controls without invented series, relations or leaked audio paths.
- 1:1 consults: `tnb-consult` computes slots server-side in Europe/Warsaw; DB exclusion constraint blocks double booking; booking, token status, cancellation and admin actions use the same Edge Function. Reminder delivery is scheduled by pg_cron to the Edge Function and authenticated with `TNB_CRON_SECRET` from Vault.
- Articles (/artykuly, articles.functions.ts): own tables articles/article_categories/article_settings, separate from community posts and library; content blocks reuse the CMS PageSection model + shared SectionsEditor/PageSections; images in private bucket article-images via `tnb-articles` only when published+released+referenced. Why: editorial texts stay separate without a second editor.
- CMS: reuse site_pages (JSONB sections) for new content pages; images via `tnb-pages` only when published+referenced.
- Legal approvals: publish snapshots store _legal.digest/publishedAt; admin_events binds snapshot UUID, actor and digest. Public readiness requires both records matching current content/publication timestamp. Draft/restore never carries authorization; legal form/status publication cannot bypass the Builder. Why: auditable exact-version approval without migrations.
- Media panel (/admin/multimedia): private bucket inventory and secure uploads are handled through the existing Supabase admin Edge Function; usage is computed from module tables and deletion is blocked while a file is referenced. Why: no duplicate storage or file-copy.

- Builder templates: `builder_templates` holds copies of PageSection config (admin-only RLS); SPA actions use `src/lib/api/templates.ts` and the `tnb-templates` Edge Function. Images are copied into `templates/<id>/` and again into the page on insert. Why: inserted copies are independent, deleting a template never breaks pages.
- Article newsletter: `tnb-article-newsletter` handles preparation, editing, test-send, explicit superadmin send and unmark actions; recipients = `newsletter_subscribers` status=active; send requires explicit confirmation and `sent` is recorded only after delivery. Why: reuse the existing list and mail engine, no auto-send.
- Library catalogue: Biblioteka TNB is the single catalogue for free, members-only and paid materials; filters live in the URL (dostep/format/kategoria/sort/q) and /materialy-premium redirects to ?dostep=premium. Why: one catalogue, no duplicate premium module.
- Biblioteka materials follow the editorial standard in src/config/editorial.ts, shown read-only at /admin/standardy; why: static content needs no table and is versioned with code.
- Library PDFs: uploads and watermark processing go through `tnb-library-admin` (original in `originals/`, only the watermarked copy becomes `file_path`; failed processing means no file served); free-material delivery/history uses `tnb-library-delivery` and every request/download is logged in `library_requests` (admin-only reads, 12-month retention). Why: no unmarked file ever served, one register.

## Home page (CMS)
- "/" renders site_pages system_key "home" only when its published sections contain `home_*` blocks (usableHome); otherwise homeDefaultSections(). Both paths and the builder use PageView → HomeBlock. Why: one renderer, never a blank or legacy home.
- Home blocks keep text in `section.settings` (keys listed in HOME_FIELDS) and lists in `items`; dynamic data (articles, posts, newsletter) stays in its modules. Builder viewer toggle uses PreviewContext, which only overrides useAuth for presentation.
- Cinematic opening is an opt-in `home_cinematic` block in existing home drafts, with five item images and named settings, rendered through HomeBlock; never add it to the built-in fallback automatically. Why: preserve public content until explicit publication without a second CMS.
- Cinematic primary CTA resolves CMS settings through home-cta and useAuth; PreviewContext changes presentation only. Why: persisted conditional destinations without changing sessions or access.
